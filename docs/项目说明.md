# Keystone 项目说明

[![Release](https://img.shields.io/badge/Release-V3.6.0-green.svg)](https://github.com/bruceblink/Keystone)
[![JDK](https://img.shields.io/badge/JDK-25-green.svg)](https://github.com/bruceblink/Keystone)

[![License](https://img.shields.io/badge/license-MIT-blue.svg)](../LICENSE)

Keystone 是一个基于 Spring Boot 3.5 的 Java 后端工程，当前定位已经从通用后台脚手架扩展为“后台管理 + Keylo 身份集成 + 船端/设备 legacy API 兼容”的综合后端。

本文档描述当前仓库状态。更偏快速上手的命令入口见 [README.md](../README.md)。

## 当前状态

| 项目 | 当前值 |
| :--- | :--- |
| 项目版本 | `3.6.0` |
| Spring Boot | `3.5.13` |
| 推荐运行 JDK | `25` |
| Java 编译目标 | `17` |

| 默认服务端口 | `18080` |
| 默认 profile | `dev` |
| 生产 / 容器默认认证模式 | `mixed` + Keylo enabled |

当前主要能力：

* Spring Security + JWT 登录认证、单账号在线会话限制、refresh token。
* local / mixed / keylo-only 三种登录模式。
* Keylo 凭证登录、Keylo bearer token 兼容认证、Keylo 用户同步注册和密码重置。
* 用户、角色、菜单、部门、岗位、字典、配置、公告、日志、在线用户等后台管理能力。
* 设备、告警、船舶、泊位、摄像头、行为配置、远程配置、文件分片、同步代理等 legacy 业务接口兼容。
* MyBatis-Plus、动态数据源、Druid、Flyway、Redis、Caffeine、本地 Map 三级缓存。
* 数据库和 Redis 密码支持 `secret:v1:aes-256-gcm` 密文文件。
* Swagger / OpenAPI 可按环境关闭，显式开启后仍受登录态保护。

```yaml
server:
  port: 18080

spring:
  config:
    import: "classpath:application-basic.yml"
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
```

公共配置在 `keystone-infrastructure/src/main/resources/application-basic.yml`，环境配置在：

| 文件 | 用途 |
| :--- | :--- |
| `keystone-admin/src/main/resources/application-dev.yml` | 本地 / 开发联调环境 |
| `keystone-admin/src/main/resources/application-prod.yml` | 生产 / 容器部署环境 |
| `keystone-admin/src/main/resources/application-test.yml` | 测试环境，H2 内存数据库 |

当前 profile 口径：

| Profile | 数据库 | Redis | 认证 |
| :--- | :--- | :--- | :--- |
| `dev` | 通过 `SPRING_DATASOURCE_*` 覆盖；当前默认指向开发环境 | 通过 `SPRING_DATA_REDIS_*` 覆盖；当前默认指向开发环境 | 当前默认 `mixed` 且 Keylo enabled |
| `prod` | MySQL，密码密文文件默认 `/run/secrets/.database_password.enc` | Redis，密码密文文件默认 `/run/secrets/.redis_password.enc` | 默认 `mixed` 且 Keylo enabled |
| `test` | H2 内存库 | 本地测试 Redis 端口 | `local`，Keylo disabled |

注意：

* `application-dev.yml` 当前包含开发联调默认值；实际部署应优先通过环境变量或外部配置覆盖，不要把开发默认值当成生产配置。
* Docker 运行时额外读取 `/app/config/`，可通过 `docker/app/config/application-prod.yml` 覆盖镜像内置配置。
* 生产环境必须显式配置 `KEYSTONE_RSA_PRIVATE_KEY`。RSA 私钥用于 `/login` 密码解密，并用于 Keystone access token 的 RS256 签名；公钥由 `/login/rsa-public-key` 提供给前端和其他服务验签。

生成 RSA 密钥对：

```bash
python scripts/secret_tool.py generate-rsa
```

## 数据库迁移

Flyway 默认迁移路径：

```text
classpath:db/migrate/common
classpath:db/migrate/mysql
```

主要目录：

```text
keystone-infrastructure/src/main/resources/db/migrate/common
keystone-infrastructure/src/main/resources/db/migrate/mysql
keystone-infrastructure/src/main/resources/db/migrate/h2
```

命名规范：

* MySQL 迁移脚本统一放在 `db/migrate/mysql/`。
* 文件名格式为 `V<版本号>__<描述>.sql`，例如 `V3_5_45__migrate_behavior_item_dictionaries.sql`。
* `__` 前后不能省略，同一版本号不能重复。
* 已执行过的 Flyway 脚本不要重命名、不要改版本号；继续演进时新增更高版本脚本。
* 脚本内容不要写死数据库名，例如不要写 `USE keystone;`。

生产环境按空库初始化，`application-prod.yml` 设置 `baseline-on-migrate=false`，非空且没有 `flyway_schema_history` 的数据库应直接启动失败。初始化脚本需要保持幂等：建表使用 `CREATE TABLE IF NOT EXISTS`，初始化数据使用 `INSERT IGNORE`，新增列和索引用 `information_schema` 条件判断后再执行 DDL。

当前 H2 测试数据由 `application-test.yml` 通过 `spring.sql.init` 加载：

```text
db/migrate/h2/keystone_schema.sql
db/migrate/h2/keystone_data.sql
```

## 认证与会话

### 登录入口

| 入口 | 用途 |
| :--- | :--- |
| `POST /login` | 统一登录入口，按 auth mode 选择 local 或 Keylo 凭证认证 |
| `POST /login/keylo` | Keylo accessToken 交换 Keystone token 的兼容入口，可关闭 |
| `POST /refresh-token` | 刷新 Keystone access token |
| `POST /logout-refresh-token` | 注销 refresh token |
| `GET /login/rsa-public-key` | 获取 Keystone RSA 公钥，用于登录密码加密和 Keystone JWT 验签 |
| `GET /captchaImage` | 获取验证码 |
| `GET /getConfig` | 获取登录页配置 |

认证模式：

| 模式 | 行为 |
| :--- | :--- |
| `local` | 使用 Keystone 本地 `sys_user.password` 认证 |
| `mixed` + `keylo.enabled=true` | `/login` 先调用 Keylo 凭证接口，再映射 Keystone 本地用户并签发 Keystone token |
| `keylo-only` | 仅允许 Keylo 认证链路 |

当前实现要点：

* mixed 模式不会在 Keylo 失败时自动回退本地登录。
* Keystone token 和 refresh token 由后端签发，登录态保存在 Redis。
* 同一账号默认只允许一个在线 access 会话；冲突时返回“该账号已经登录”，客户端可用 `forceLogin=true` 显式接管旧会话。
* 受保护接口可直接携带 Keylo accessToken；该路径只校验 Keylo token，不要求映射 `sys_user`，并构建临时安全主体。

* [refresh-token-session-design.md](refresh-token-session-design.md)
* [keylo-token-integration-plan.md](keylo-token-integration-plan.md)

## Keylo 集成与用户注册流程

### 定位

Keystone 是后台业务和本地 RBAC 权限中心；Keylo 是可选身份中心，负责外部身份认证与令牌签发。

Keystone 不把本地权限完全替换成 Keylo 权限。`/login` 场景仍会把 Keylo 身份映射到 `sys_user`，再使用 Keystone 的用户、角色、菜单和权限模型。

### 身份映射

| Keystone 字段 | 来源 | 用途 |
| :--- | :--- | :--- |
| `sys_user.external_user_id` | Keylo token 的 `uid`，或创建用户响应的 `id` | 普通用户主映射键 |
| `sys_user.external_subject` | Keylo token 的 `sub`，或 `subject-template` 推导值 | 兜底映射键 |

登录映射顺序：

1. 优先使用 `uid -> sys_user.external_user_id`。
2. 找不到时使用 `sub -> sys_user.external_subject`。
3. 仍找不到则返回 Keystone 用户不存在。

### 新增用户同步注册

在 Keystone 新增用户时：

1. 先在 Keystone 创建 `sys_user`。
2. 当 `keystone.auth.keylo.provisioning.enabled=true` 时，调用 Keylo 管理接口创建用户。
3. 先调用 Keylo 管理员令牌接口获取 `access_token`。
4. 再调用创建用户接口。
5. 从 Keylo 响应提取用户 ID，默认字段 `id`，回填 `sys_user.external_user_id`。
6. 从 Keylo 响应提取 `sub`；如果响应没有 `sub`，按 `subject-template`，默认 `user:{username}`，推导并回填 `sys_user.external_subject`。

如果 Keylo 注册失败，会抛出业务异常并回滚新增用户流程。

管理员重置用户密码时，如果 Keylo provisioning 已开启，Keystone 会先调用 Keylo 重置密码接口。缺少 `sys_user.external_user_id`、Keylo 重置密码 URL 未配置或 Keylo 返回失败时，请求会直接失败，不会继续修改 Keystone 本地密码，避免 mixed 模式下本地密码与 Keylo 密码不一致。

### 关键配置

```yaml
keystone:
  auth:
    mode: ${KEYSTONE_AUTH_MODE:local}
    keylo:
      enabled: ${KEYSTONE_AUTH_KEYLO_ENABLED:false}
      base-url: ${KEYLO_BASE_URL:http://keylo:2345}
      issuer-uri: ${KEYLO_ISSUER_URI:${keystone.auth.keylo.base-url}}
      trusted-issuers: ${KEYLO_TRUSTED_ISSUERS:${keystone.auth.keylo.issuer-uri}}
      jwk-set-uri: ${KEYLO_JWK_SET_URI:${keystone.auth.keylo.base-url}/.well-known/jwks.json}
      audiences: ${KEYLO_AUDIENCES:admin-backend}
      credential-verify-url: ${KEYLO_CREDENTIAL_VERIFY_URL:${keystone.auth.keylo.base-url}/v1/auth/token}
      legacy-token-login-enabled: ${KEYLO_LEGACY_TOKEN_LOGIN_ENABLED:true}
      provisioning:
        enabled: ${KEYLO_PROVISIONING_ENABLED:true}
        admin-client-id: ${KEYLO_ADMIN_CLIENT_ID:cli-admin-root}
        admin-client-secret: ${KEYLO_ADMIN_CLIENT_SECRET:replace-with-strong-admin-secret}
        create-user-url: ${KEYLO_CREATE_USER_URL:${keystone.auth.keylo.base-url}/v1/admin/users}
        reset-password-url-template: ${KEYLO_RESET_PASSWORD_URL_TEMPLATE:${keystone.auth.keylo.base-url}/v1/admin/users/{userId}/reset-password}
        admin-token-url: ${KEYLO_ADMIN_TOKEN_URL:${keystone.auth.keylo.base-url}/v1/admin/token}
        subject-template: ${KEYLO_SUBJECT_TEMPLATE:user:{username}}
        user-id-field: ${KEYLO_USER_ID_FIELD:id}
```

### 配置字段与启动校验

* 普通用户映射字段：`sys_user.external_user_id`
* Keylo 登录兜底映射字段：`sys_user.external_subject`
* 登录主体映射：默认使用 Keylo `sub` claim（可通过 `KEYLO_SUBJECT_CLAIM` 调整）
* 登录用户 ID 映射：默认使用 Keylo `uid` claim（可通过 `KEYLO_USER_ID_CLAIM` 调整）
* Keylo 服务地址：默认通过 `KEYLO_BASE_URL` 派生 issuer、JWKS、凭证登录、用户创建和管理员 token 地址；当实际签发 token 的 `iss` 与访问地址不一致时，可通过 `KEYLO_TRUSTED_ISSUERS` 配置可信 issuer，例如 `keylo`。
* Keylo token 受众校验：默认信任 `admin-backend`，可通过 `KEYLO_AUDIENCES` 配置多个 audience。
* Keylo 凭证登录：先向 Keylo 换取 accessToken，再复用 Keystone 内部 `KeyloTokenVerifier` 完成 JWT 验签、issuer、audience 和时间校验。
* Keylo 凭证登录错误包装：`400/401/403` 会返回 Keystone 的 `Business.LOGIN_WRONG_USER_PASSWORD`；Keylo 服务异常或响应格式异常会返回 `Business.LOGIN_ERROR`，不直接暴露 Keylo 原始响应。
* Keylo bearer token 直通：受保护接口直接携带 Keylo accessToken 时，校验通过即创建临时 Keystone 安全主体，不要求 `sys_user` 映射。
* 生产启动强校验：`KEYSTONE_RSA_PRIVATE_KEY` 必须显式配置；当 `auth.mode=mixed` 或 `auth.mode=keylo-only` 时，还会校验 Keylo 服务地址、issuer/JWKS、audience 与凭证登录地址等实际认证所需配置。不再把 Druid 监控密码作为 mixed 模式启动前置条件。
* 新增错误码：`Business.LOGIN_KEYLO_PROVISION_FAILED`

### Keylo 用户数据丢失恢复

当 Keylo 用户库丢失但 Keystone 本地库仍保留 `sys_user` 时，`auth.mode=mixed` 且 `keylo.enabled=true` 的 `/login` 会先调用 Keylo 凭证校验接口。此时登录失败是预期行为，因为 Keystone 还无法取得 Keylo token，也无法通过 `uid -> sys_user.external_user_id` 或 `sub -> sys_user.external_subject` 完成本地用户映射。

恢复优先级如下：

1. 若存在 Keylo 数据库备份，优先恢复 Keylo 数据库。该方式可以保留原 Keylo 用户 ID、密码、token 映射和 `sys_user.external_user_id` 关联，通常不需要修改 Keystone 用户表。
2. 若没有 Keylo 备份，只能重建 Keylo 用户并回填 Keystone 映射。原 Keylo 密码不可从 Keystone 的 BCrypt 密码哈希反推出，需要为用户设置临时密码并要求后续改密。

无 Keylo 备份时，按以下步骤处理：

1. 临时切换 Keystone 为本地登录，恢复后台访问能力。

```env
KEYSTONE_AUTH_MODE=local
KEYSTONE_AUTH_KEYLO_ENABLED=false
```

修改后重启 Keystone。生产 / 容器默认是 mixed 模式，抢修结束后需要再切回。

2. 备份 Keystone 用户表。

```sql
CREATE TABLE sys_user_before_keylo_repair_20260605 AS
SELECT * FROM sys_user;
```

3. 导出需要重建 Keylo 账号的本地用户。

```sql
SELECT user_id,
       username,
       nickname,
       email,
       phone_number,
       external_user_id,
       external_subject
FROM sys_user
WHERE deleted = 0;
```

4. 逐个调用 Keylo 管理接口重新创建用户。

Keylo 创建用户接口默认由 `KEYLO_CREATE_USER_URL` 指定，默认路径为：

```text
${KEYLO_BASE_URL}/v1/admin/users
```

请求字段与 Keystone 新增用户同步注册逻辑一致：

```json
{
  "username": "admin",
  "nickname": "管理员",
  "email": "admin@example.com",
  "phoneNumber": "13800000000",
  "password": "Temp#Password123"
}
```

创建前需要先通过 `KEYLO_ADMIN_TOKEN_URL` 获取管理员 `access_token`。Keylo 创建成功后，记录响应中的用户 ID，默认字段为 `id`。如果响应没有 `sub`，按当前默认模板推导为 `user:{username}`。

5. 回填 Keystone 本地用户映射。

```sql
UPDATE sys_user
SET external_user_id = '<new-keylo-user-id>',
    external_subject = 'user:<username>',
    update_time = NOW()
WHERE user_id = <keystone-user-id>;
```

其中：

* `external_user_id` 对应 Keylo 用户 ID，默认来自 Keylo 创建用户响应的 `id` 字段。
* `external_subject` 对应 Keylo token 的 `sub`，默认模板为 `user:{username}`。

6. 切回 mixed 模式并重启 Keystone。

```env
KEYSTONE_AUTH_MODE=mixed
KEYSTONE_AUTH_KEYLO_ENABLED=true
```

7. 使用临时密码验证 `/login`。登录成功后，通知用户修改为新密码；管理员重置密码时，Keystone 会在存在 `external_user_id` 的情况下同步调用 Keylo 重置密码接口。

注意事项：

* 现有应用只在新增 Keystone 用户时自动创建 Keylo 用户并回填映射；对已有用户没有内置批量重建入口。
* 仅修改 `sys_user.password` 不能修复 mixed 登录，因为 mixed 模式的密码校验先发生在 Keylo。
* 不要随意清空 `external_user_id` / `external_subject` 后直接切回 mixed，否则 `/login` 即使通过 Keylo 校验，也可能无法映射到 Keystone 本地用户。
